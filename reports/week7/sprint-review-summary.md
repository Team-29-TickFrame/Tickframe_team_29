# Sprint Review Summary

## Sprint Review Overview
The Week 7 Sprint Review was conducted at the end of Sprint 5 to present the final MVP v3, discuss the completed work, review the remaining follow-up issues from the previous Sprint, evaluate deployment and transition readiness, and collect final customer feedback.

The same meeting also included a discussion of deployment, operational documentation, transition readiness, and customer feedback. A separate customer-executed UAT session was not conducted during this meeting.

## Planned Sprint 5 Goal
The planned goal for Sprint 5 was to finalize MVP v3 and prepare the product for transition by:

* completing the remaining customer-requested improvements;
* improving the reliability of ML-based pattern detection;
* resolving issues identified during the previous Sprint Review;
* improving deployment and operational documentation;
* preparing the system for customer use and future maintenance.

## Delivered MVP v3
The team presented the completed MVP v3 and discussed the latest improvements.

The delivered version includes:
* real-time cryptocurrency market monitoring;
* historical candle collection and storage;
* ML-based chart pattern recognition;
* rule-based validation of detected patterns;
* pattern visualization on TradingView-style charts;
* Docker Compose deployment;
* frontend, backend, PostgreSQL, TimescaleDB, and Grafana services;
* documented environment configuration using .env and .env.example;
* repository documentation with deployment instructions;
* maintenance scripts for downloading historical candle data;
* a new interface section for operational scripts that is being finalized.

The customer reviewed the delivered functionality and discussed the remaining improvements before project completion.

## Resolved Follow-Up Issues from Week 6
The Sprint Review confirmed that several issues identified after the previous Sprint had been addressed.

The most significant completed improvement was the correction of the ML visualization inconsistency.

Previously, the ML model could recognize a pattern while the rule-based detector rejected it, resulting in a pattern name being displayed without any visualization on the chart.

The updated implementation now compares the labels returned by both detection methods. If the labels do not match, the detected pattern is treated as unconfirmed and nothing is displayed to the user.

The team also demonstrated that:

* model evaluation metrics are stored and available for inspection;
* deployment documentation is available in the repository;
* environment configuration files have been prepared;
* historical candle-loading scripts are documented;
* the project structure has been updated for easier maintenance.

## Unresolved Follow-Up Issues
The following improvements were discussed but were not yet fully completed during the review:

* adding a frontend switch that allows users to choose between ML-based and rule-based pattern detection;
* completing the interface for launching maintenance scripts directly from the frontend;
* finishing migration of all required configuration variables into the documented environment configuration;
* continuing improvements to the experimental ML component.

The customer specifically requested the detection-method switch, and the team agreed to implement it because both detection approaches already exist in the current architecture.

## Machine Learning Discussion
A significant part of the Sprint Review focused on the experimental ML subsystem.

The team explained that the model operates on windows of 96 closed candles.

Historical market data is first labeled using the rule-based detector. Feature values such as trend, volatility, compression, and other calculated indicators are extracted for every window.

After dataset balancing, the model is trained using historical examples.

The current implementation uses a LightGBM classifier that predicts the most probable chart pattern.

The rule-based detector is then used to validate the prediction before visualization is displayed.

The team clarified that the ML model predicts the pattern label only. It does not predict the exact vertices required for drawing pattern boundaries, therefore the rule-based detector remains necessary for visualization.

## Model Evaluation
During the review, the customer requested the current model quality metrics.

The team opened the stored evaluation files and reviewed the available results.

For the one-minute timeframe, the model currently reports approximately:
* Accuracy: 0.75
* Macro F1-score: 0.76

Additional reported metrics include:
* Precision
* Recall
* F1-score
* Confusion Matrix
* Per-class evaluation metrics

The customer confirmed that the reported accuracy is calculated relative to the labels generated by the rule-based detector.

## Customer Feedback
During the review the customer provided several suggestions.

The primary requested improvement was adding a switch allowing users to choose between:

* ML-based pattern detection;
* rule-based pattern detection.

The customer considered this feature useful for comparing both detection approaches and evaluating the experimental ML component.

The customer also requested that maintenance scripts be accessible directly through the application interface instead of requiring manual execution.

## Remaining Risks and Post-Course Limitations

The following limitations remain after the completion of Sprint 5:
* the ML component is still experimental;
* ML predictions depend on rule-based labeling;
* visualization still requires rule-based validation;
* the current ML model does not independently predict visualization boundaries;
* reported evaluation metrics are measured relative to rule-based labels rather than independently verified market ground truth;
* additional validation using larger historical datasets would improve confidence in the model;
* the frontend switch between ML and rule-based detection remains to be completed;
* maintenance scripts are still being integrated into the frontend interface.

These limitations do not prevent the system from operating but represent opportunities for future development after the course.


## Sprint Review Outcome
The customer confirmed that MVP v3 provides the planned functionality and that the overall architecture, deployment process, documentation, and operational workflow are understandable.
